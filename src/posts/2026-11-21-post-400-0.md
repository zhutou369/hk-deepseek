上星期有位做中小企 IT 的朋友找我，說公司買了一張 8GB VRAM 的顯卡，興致勃勃想本地跑 DeepSeek，結果一載入模型就報記憶體不足，畫面直接卡死。這種情況其實很常見：模型本身的參數量，跟顯卡記憶體是兩回事，中間還有一道量化與卸載的門檻。

我測試時發現，只要願意在「速度」和「畫質」（其實是推理精度）之間做取捨，8GB 卡一樣跑得動 7B 級別的 DeepSeek 蒸餾模型。以下是我實際調過的流程。

## 先搞清楚：你卡在哪裡

報錯通常是 `CUDA out of memory` 或 Ollama 直接 crash。先分清楚兩種情況：一種是模型權重本身放不進 VRAM，另一種是權重放得進、但推理時的 KV cache 爆掉。前者靠量化，後者靠減少 context 長度或卸載層數。

以 Ollama 為例（我測試用的是 0.5.x 版本，具體版本號以官方文檔為準），執行 `ollama run` 時它會自動選 quantization，但預設不一定最省。你可以用 `ollama ps` 看目前模型佔用的記憶體，再決定下一步。

## 三步設定：量化 + 部分卸載

**第一步：換成更小的量化版本。** 7B 模型用 Q4_K_M 大約 4–5GB，8GB 卡勉強夠；Q8 就別想了。在 Modelfile 裡指定量化，或在 pull 時選對應 tag。

**第二步：限制 GPU 卸載層數。** Ollama 支援 `num_gpu` 參數，把部分層留在 CPU。做法是在 Modelfile 加 `PARAMETER num_gpu 20` 之類，具體層數要試，先給一個保守值再往上加。

**第三步：收窄 context。** 預設 context 太長會吃光 KV cache，把 `num_ctx` 降到 2048 或 4096，通常就穩了。

這三步做完，多數 8GB 卡都能跑起來。詳細的本地安裝流程可以參考站內的 [Ollama 本地部署教學](/posts/deepseek-ollama-local-setup/)，那邊有完整的環境準備步驟。

## 混合推理的取捨

所謂混合推理，就是一部分層跑 GPU、一部分跑 CPU。好處是「能跑」，代價是速度。我實測 7B Q4 模型，全 GPU 大約每秒 20+ token，卸載一半到 CPU 後掉到每秒 5–8 token 左右，差別很明顯。

所以取捨點很簡單：如果你只是做批次處理、離線摘要、RAG 檢索後生成，慢一點無所謂；但如果是即時對話，建議縮小模型或升級顯卡。中小企場景裡，我會建議先用量化版跑通流程，再按實際瓶頸決定要不要加卡。

另外，如果你打算接 API 做對比，可以看 [DeepSeek API 的 key 與限制說明](/posts/deepseek-api-key-and-limits/)，本地和雲端各有利弊。

## 常見問題

**Q1：8GB VRAM 最多能跑多大的 DeepSeek？**
以 7B 蒸餾模型配 Q4 量化較穩妥，更大參數要麼卸載更多層，要麼直接跑不動。具體支援的模型清單以官方文檔為準。

**Q2：量化會不會讓回答變差？**
Q4 相對 Q8 會有精度損失，但日常問答多數感覺不明顯；涉及精確數值或程式碼生成時，建議實測對比。

**Q3：為什麼設定了 num_gpu 還是爆記憶體？**
多半是 context 太長或同時開了其他佔用 GPU 的程式，先關掉再試。

**Q4：CPU 推理很慢怎麼辦？**
檢查是否用了多執行緒，以及記憶體頻寬是否夠；筆記本 CPU 通常比桌面弱一截。

**Q5：本地跑和用官方 API 怎麼選？**
涉及敏感資料、要離線，走本地；追求速度和穩定，走 API。混合用法也很常見，提示詞設計可以參考 [提示詞基礎教學](/posts/deepseek-prompt-basics/)。

以上參數與報錯處理，不確定的細節請以官方文檔為準。
