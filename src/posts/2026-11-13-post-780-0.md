## 問題場景：回覆突然被切斷

上週升級咗個客服機械人，用 DeepSeek API 版本 `deepseek-chat`（2025 年 3 月嘅定價頁面仲寫住每百萬 tokens 幾多錢，以官方文檔為準）。本來答得好地地，但一遇到長問題就只出半截答案，結尾仲要硬生生斷開。我測試時發現，好多時唔係模型唔識答，而係 `max_tokens` 同 context window 夾唔埋，輸出被截斷。

呢篇就係我踩過嘅坑，同埋實際排查步驟。如果你都試過 API 回覆「講講下冇咗」，可以跟住做。

## 第一步：檢查 max_tokens 設定

`max_tokens` 係你要求模型最多生成幾多個 token 嘅上限。呢個參數只管「輸出」，唔關輸入事。但如果你設定得太細，例如 256，模型答到一半就冇 quota，自然會被截斷。

操作步驟：

1. 打開你嘅 API 請求代碼，搵出 `max_tokens` 參數。
2. 將佢暫時調高到 1024 或 2048（視乎你嘅 context window 大小，下面會講）。
3. 再發送同一條問題，睇下回覆係咪完整。

我試過有個 case，`max_tokens` 設咗 300，但問題要求「列舉五點並解釋」，結果第四點就斷咗。調高到 800 之後就正常返。記住，`max_tokens` 只係輸出上限，唔會影響輸入長度。

## 第二步：理解 context window 的組成

Context window 係模型一次過可以處理嘅總 token 數，包括你嘅輸入（prompt）同模型嘅輸出（completion）。DeepSeek 嘅 API 文檔寫明，唔同模型有唔同嘅 context window 大小，例如 `deepseek-chat` 支援 64K tokens（以官方文檔為準）。呢個 64K 係輸入加輸出嘅總和。

即係話，如果你嘅 prompt 已經用咗 60K tokens，咁你最多只能設定 `max_tokens` 為 4K 左右，否則就會超出 context window，API 可能會報錯或者自動截斷。

我試過用 RAG 場景，將一大段文件塞入 prompt，結果 `max_tokens` 設咗 4096，但 prompt 太長，最終回應被 Cut。後來我用 token 計數工具（例如 `tiktoken`）估算 prompt 長度，再預留輸出空間，問題就解決咗。

## 第三步：實測與調整策略

要避免截斷，你可以跟住呢個流程：

1. 用 tokenizer 計算 prompt 嘅 token 數（可以參考 [DeepSeek API 密鑰與限制說明](/posts/deepseek-api-key-and-limits/) 入面嘅工具推薦）。
2. 用 context window 總數減去 prompt token 數，得到可用輸出空間。
3. 將 `max_tokens` 設定為可用輸出空間嘅 80% 左右，留啲緩衝。
4. 如果回覆仍然被截斷，檢查 API 回應嘅 `finish_reason` 欄位：如果係 `length`，即代表達到 `max_tokens` 上限；如果係 `stop`，就正常結束。

另外，如果你需要成日處理長文本，可以考慮用 [DeepSeek 本地 Ollama 部署](/posts/deepseek-ollama-local-setup/) 嘅方式，自己控制資源，但就要注意本地模型嘅 context window 可能唔同。

## 常見問題

**Q1：`max_tokens` 設定得越大越好？**

唔係。設定太大但 prompt 又長，會超出 context window，導致報錯或截斷。應該按實際需要設定，並預留 buffer。

**Q2：點解 API 回覆冇报错但内容被截斷？**

最常見係 `max_tokens` 用盡，`finish_reason` 會顯示 `length`。你可以檢查回應 JSON 入面嘅 `finish_reason` 確認。

**Q3：context window 係咪固定不變？**

唔同模型版本有唔同大小，而且官方可能會更新。建議每次升級模型後，重新睇一次官方文檔嘅 context window 說明。

**Q4：如何避免 prompt 太長？**

可以精簡 prompt、用摘要技巧，或者將長文件分塊處理。如果係 RAG 應用，可以參考 [DeepSeek Prompt 基礎教學](/posts/deepseek-prompt-basics/) 入面嘅分段策略。

**Q5：如果遇到 API 錯誤碼，點排查？**

可以睇 [DeepSeek API 重試指南](/posts/deepseek-api-retry-guide/)，入面有常見錯誤碼同處理方法。
