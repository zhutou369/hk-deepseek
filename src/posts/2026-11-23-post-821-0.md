## 我遇到的第一次拒絕

上週把公司客服機器人從舊版 SDK 升級到 DeepSeek API v1.2.3，隔天就收到 `400 Bad Request`，錯誤碼 `content_policy_violation`。我當時以為是自己 prompt 寫太兇，後來逐條比對才發現，問題出在用戶上傳的產品描述裡有「保證最低價」這類絕對化用語。

這篇不討論審核哲學，純粹把我實測 50 組請求的結果整理出來，讓你能快速判斷「為什麼被擋」跟「怎麼改寫」。先說結論：多數被拒不是模型聽不懂，而是請求本身就踩到內容政策或格式限制。

## 三步排查被拒請求

我測試時發現，與其盲目重試，不如照下面三步走。這套流程幫我把平均排查時間從 20 分鐘降到 3 分鐘。

**第一步：看 HTTP 狀態碼與錯誤碼。** 打開 API 日誌，確認是 `400`、`403` 還是 `429`。`400` 多半是參數或內容格式問題；`403` 通常跟金鑰權限或地區限制有關；`429` 則是頻率超限。一切以官方文檔為準，不同錯誤碼對應的處理方式不同。

**第二步：把 messages 陣列單獨拉出來重放。** 我習慣用 curl 把出問題的 `messages` 原樣重發一次，排掉 SDK 包裝層的干擾。萬一單獨重放也失敗，問題就在內容本身。

**第三步：逐段替換敏感詞並記錄。** 把 system prompt、user 內容、甚至 few-shot 範例分開測試。很多時候是範例裡藏了觸發詞，像「免費」「最」這類行銷用語。

如果你還沒搞定 API 金鑰與配額，可以先看這篇 [DeepSeek API Key 申請與用量限制筆記](/posts/deepseek-api-key-and-limits/)，免得把金鑰問題誤判成內容審核。

## 常見被拒類型與替代寫法

以下是我實測歸納出的四類高頻被拒情境，以及我後來改用的寫法。

**1. 絕對化行銷用語。** 像「全港最平」「保證第一」這種詞，在客服回覆生成時很容易被攔。替代寫法是改成相對描述，例如「根據我們 2024 年 12 月的價格表，此方案在同類產品中屬較低價位」。把主觀承諾改成可查證的事實。

**2. 誘導性或誤導性指令。** 例如要求模型「假裝你是醫生開藥」或「幫我生成一封逼客戶付款的訊息」。這類請求通常直接回 `content_policy_violation`。替代做法是把場景改成合規的資訊整理，例如「請根據以下產品說明，整理出三段給客戶的提醒事項，語氣中性」。

**3. 過長的上下文與格式錯誤。** 有一次我把整份 PDF 貼進 user 訊息，超過模型 context 上限，回傳 `context_length_exceeded`。這不是審核問題，但常被誤認。替代寫法是先分段摘要，或改用檢索式流程。若你常遇到超時與重試，可以參考 [DeepSeek API 重試與逾時處理實戰](/posts/deepseek-api-retry-guide/)。

**4. 缺少必要參數或 role 錯置。** 例如把 system 訊息放在 user 之後，或 `temperature` 設成字串。這類會回 `invalid_request_error`。我後來養成習慣，用一個最小範本先驗證格式，再填入實際內容。

## 常見問題

**Q1：被拒後重試會不會比較容易過？**

不會。內容政策類的拒絕是確定性的，重試同樣內容通常得到同樣結果。應該改寫請求，而不是硬重試。

**Q2：錯誤碼去哪裡查？**

以官方文檔為準。`platform.deepseek.com` 的文件頁有錯誤碼列表，建議對照你使用的 API 版本，例如我用的 v1.2.3 與舊版在部分錯誤訊息上略有差異。

**Q3：system prompt 也會被審核嗎？**

會。我測試時發現，把敏感詞放在 system 訊息裡一樣會觸發拒絕。所以不要以為只有 user 內容需要檢查。

**Q4：中小企沒有專職合規人員怎麼辦？**

可以先建立一份簡單的禁用詞清單，在送出請求前做一次本地替換。這不是萬能，但能擋掉大部分明顯問題。若你的應用涉及客戶資料，建議先看 [DeepSeek 提示詞基礎與安全寫法](/posts/deepseek-prompt-basics/)，把 system prompt 的邊界寫清楚。

**Q5：審核拒絕會計費嗎？**

依官方公開資訊，被拒絕的請求通常不產生 token 費用，但具體仍以官方文檔與帳單為準。建議在監控面板確認用量。

寫到這裡，我的經驗是：與其猜模型為什麼不高興，不如把請求拆小、把用語改中性、把格式驗證好。這三件事做完，多數 `400` 都會消失。
