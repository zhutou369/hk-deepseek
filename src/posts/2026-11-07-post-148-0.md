## 實測背景：我用邊個版本？

上週升級咗 DeepSeek 嘅 API 版本（2024 年 11 月嘅穩定版），見到官方文檔寫明上下文窗口有 128K tokens。但係「tokens」同「頁數」之間點換算，好多普通用戶都一頭霧水。我測試時發現，網上講法好混亂，有人話 100 頁，有人話 300 頁，於是決定自己落手實測。

今次測試只用官方公開嘅 API 接口，唔會編造模型能力。如果你仲未搞掂 API key 同限額，建議先睇吓[呢篇 API Key 與限額教學](/posts/deepseek-api-key-and-limits/)，免得中途卡住。

## 三步實測流程（附截圖描述）

**第一步：準備測試文件**
我用咗三種常見格式：純文字 TXT、Word 導出嘅 PDF、同埋網頁另存嘅 HTML。每份文件都用 `wc -w` 或 PDF 工具計字數，再換算成中文字數（一個中文字大約等於 1 至 1.5 tokens，以官方文檔為準）。測試文件嘅頁數由 10 頁到 200 頁不等。

**第二步：用 API 逐份餵入**
寫咗個簡單 Python script，將文件內容放入 `messages` 陣列，每次只改 `content` 長度，其他參數固定（temperature 0.7，max_tokens 512）。如果遇到 400 報錯，就記錄低當時嘅 token 數。呢度可以參考[重試機制指南](/posts/deepseek-api-retry-guide/)嚟處理偶發錯誤。

**第三步：記錄成功與失敗臨界點**
每次成功回應就加多 10 頁，直到出現「context length exceeded」之類嘅報錯。截圖描述：API 回應 JSON 入面，`usage` 欄位會顯示 `prompt_tokens`，我就係靠呢個數去對比頁數。

## 實測結果：一次過讀到幾多頁？

先講結論：以 128K tokens 上下文計，**純中文文件大約可以讀 180 至 220 頁**（假設每頁 500 字，每字約 1.2 tokens）。我測試時發現，PDF 因為有排版、頁眉頁腳同圖片描述，實際有效字數會少啲，大約 150 至 180 頁就會頂到上限。英文文件反而可以多啲，因為英文字詞 token 效率高，大約 250 至 300 頁。

不過要留意，呢個數字係指「一次過輸入」嘅極限，如果文件太長，模型回應質素會下降，甚至漏答重點。所以實用上，我建議每次餵 80 至 120 頁，留返空間俾對話歷史同模型輸出。

如果你用 Ollama 跑本地模型，上下文長度設定又唔同，可以睇[本地部署教學](/posts/deepseek-ollama-local-setup/)調整 `num_ctx` 參數。

## 常見問題

**Q1：點解我餵 100 頁 PDF 就報錯？**
可能係 PDF 入面有大量表格或圖片，轉成文字後 token 數暴增。建議先用工具抽出純文字，再餵入模型。

**Q2：上下文長度係咪越大越好？**
唔係。太長嘅上下文會拖慢回應速度，而且模型可能忽略中間部分。以官方文檔為準，按需選擇。

**Q3：點樣知道實際用咗幾多 tokens？**
API 回應嘅 `usage.prompt_tokens` 會顯示，自己寫 script 記錄低就得。

**Q4：文件超過上限點算？**
可以分段餵入，或者用摘要技巧，先叫模型總結每段，再合併。呢度有[提示詞基礎教學](/posts/deepseek-prompt-basics/)可以參考。

**Q5：免費額度夠唔夠測試？**
以官方公佈為準，一般幾百頁文件會用掉一定額度，建議先睇限額說明。

## 實用技巧：點樣餵文件最慳 token

1. **清理格式**：刪走頁眉頁腳、重複標題、多餘空行，可以慳 10% 至 20% tokens。
2. **用 TXT 代替 PDF**：純文字檔案 token 效率最高，避免 PDF 嘅隱藏字符。
3. **分段對話**：如果文件太長，分成幾次餵，每次叫模型記住重點，比一次過塞入更穩定。
4. **監控 usage**：每次 API 回應都檢查 `prompt_tokens`，養成習慣。

最後提提你，如果登入網頁版遇到問題，可以睇[登入排錯指南](/posts/deepseek-web-login-troubleshoot/)。希望呢篇實測幫到你預算文件頁數，唔好再盲試。
