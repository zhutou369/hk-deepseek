## 為什麼你的 API 又報錯？先看版本和日期

上星期幫一間觀塘中小企拆局，他們用 DeepSeek API 做客服自動回覆，整個 workflow 突然掛了。打開 log 一看，紅色一大片：401、429、503 輪流出現。我順手記下當時環境——2025 年 6 月中，API 版本行 `deepseek-chat`，計費方式是按 token 預付。這篇就是當日排查記錄整理出來的，你對著自己的 error code 跳到相應段落就行。

先講個大原則：DeepSeek 的錯誤碼設計很直接，數字開頭已經告訴你是哪一類問題。4xx 多數是你送出去的 request 有問題，5xx 就是伺服器那邊頂不住。搞清楚這點，排查時間至少省一半。

## 401：金鑰不對，還是過期了？

401 最常見，也最容易搞錯方向。我第一次接 API 時，以為 401 等於「金鑰打錯」，結果查了半個鐘，才發現是環境變數讀取失敗，key 根本沒載入。

401 的原因通常就三個：key 打錯或漏字、key 已經被 revoke、請求 header 沒帶 `Authorization: Bearer <key>`。你可以用以下步驟快速驗證：

1. 打開終端機，用 curl 直接打一次最簡請求，不經過你的框架：
   `curl https://api.deepseek.com/models -H "Authorization: Bearer $DEEPSEEK_API_KEY"`
2. 如果 curl 成功但程式失敗，九成是你的 .env 或 secrets manager 沒正確載入，檢查變數名有沒有多空格。
3. 如果 curl 也 401，進 platform.deepseek.com 後台重新生成一條 key，同時確認舊 key 已經刪除。

記住：key 不要寫死在前端，也不要 commit 上 git。這點跟怎麼管理 API 金鑰和額度上限是同一個道理，有興趣可以看[API 金鑰與額度管理實戰](/posts/deepseek-api-key-and-limits/)。

## 402：餘額見底，別急著充值

402 是「Payment Required」，即你的 account 沒錢或者額度用完。聽起來很簡單，但實際上有個坑：預付制下，如果你設了自動充值上限，餘額低過某個數就會停。

我試過一次，dashboard 顯示還有幾塊錢，但 API 照樣 402。後來發現是「贈送額度」和「現金餘額」分開計，贈送額度用完但現金未扣，系統都會攔。處理方法：

1. 進 platform.deepseek.com 的 Billing 頁，看清楚「可用餘額」和「凍結額度」兩欄。
2. 如果真的沒錢，充值後等 1 至 2 分鐘再試，別立刻狂 retry，否則很容易觸發 429。
3. 如果餘額充足也 402，開 ticket 問客服，附上 request ID 和時間戳。

順帶一提，如果你用免費額度做測試，記得定期 check 用量，別等到 production 才爆。

## 422：參數格式錯，多數死在 JSON

422 是「Unprocessable Entity」，即你的 request 格式對，但內容有問題。最常見是 `messages` 陣列結構錯、`temperature` 超出範圍、或者 `max_tokens` 設得太離譜。

上個月有個朋友找我，說 API 一 call 就 422，我看了他的 payload 五秒就笑了——他把 `messages` 寫成 object，但 API 要 array。正確格式是：

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "user", "content": "你好"}
  ]
}
```

排查步驟：

1. 用 Postman 或 curl 把你個 payload 原封不動打一次，看 error message 有沒有講哪個 field 出事。
2. 對照官方文檔的 request schema，特別留意 `role` 只可以是 `system`、`user`、`assistant`。
3. 如果用到 function calling 或 JSON mode，確認有沒有漏掉必要的 `tools` 或 `response_format` 參數。

422 的 error body 通常會直接指出哪個參數不對，別只看 status code 就收工。

## 429：請求太密，要懂得排隊

429 是「Too Many Requests」，即你的請求頻率超過了限流閾值。這個錯誤在批量處理或者 RAG 檢索時特別常見，因為你會短時間內打幾十個 request。

我測試時發現，DeepSeek 的限流是按分鐘計，而且不同 model 有不同上限。最簡單的解決方法是加 exponential backoff：第一次等 1 秒，第二次等 2 秒，第三次等 4 秒，如此類推。如果你用 Python，可以參考[API 重試機制實戰指南](/posts/deepseek-api-retry-guide/)裡面的範例。

另外，如果你的 workflow 有大量並行請求，建議加一個 queue 或者 semaphore，控制同時發出的請求數量。別一次過放 100 個 request 出去，否則你只會不停吃 429。

## 503：伺服器繁忙，不是你的錯

503 是「Service Unavailable」，代表 DeepSeek 那邊臨時頂不住，可能是流量高峰或者維護。這時候你的程式碼沒問題，唯一可以做的就是等。

我上週升級後就撞正一次 503，整個下午斷斷續續。處理方法：

1. 先去 DeepSeek status page 或官方社交帳號看有沒有公告。
2. 如果只是短暫 503，加 retry 邏輯，等 5 至 10 秒再試。
3. 如果持續超過 15 分鐘，考慮切換到備用 model 或者暫時降級功能，別硬等。

記住：503 不關你 key 的事，也不關你 payload 的事，別亂改參數。

## 三步通用排查流程

無論你遇到哪個錯誤碼，都可以跟這三步走：

1. **看 error body**：DeepSeek 的 response 多數會包一段 `error.message`，直接講明原因，別只看 status code。
2. **隔離變數**：用 curl 打最簡請求，如果 curl 成功就代表問題在你框架或環境；如果 curl 失敗就代表問題在 key、餘額或網絡。
3. **查文檔 + 搜 error code**：官方文檔有齊每個錯誤碼的定義，不確定的細節以官方文檔為準。

## 常見問題

**Q1：401 和 403 有什麼分別？**
401 是「未認證」，即你沒帶 key 或者 key 錯；403 是「已認證但沒權限」，例如你 key 沒開某個 model 的 access。DeepSeek 目前主要出 401，403 較少見。

**Q2：402 是不是一定沒錢？**
不一定。有時是 billing 系統延遲，或者你信用卡過數失敗。先看 Billing 頁，再等幾分鐘，最後才開 ticket。

**Q3：429 會不會封號？**
正常不會，429 只是限流，不是懲罰。但如果你無視 429 瘋狂 retry，有可能被暫時封 IP，所以一定要加 backoff。

**Q4：503 期間我應該轉用其他 model 嗎？**
如果是短暫 503，等一陣就行；如果是大規模故障，可以考慮轉用其他供應商的 model 做 fallback，但記得要改 base URL 和 API key。

**Q5：怎麼知道哪個錯誤碼最常出現？**
你可以在程式裡加一個簡單的 counter，將每次 error code 寫入 log，一星期後看哪個最多，就針對那個做優化。

搞定以上幾點，基本上九成 API 錯誤都可以自己解決。下次再撞到紅色 error，別慌，對著 code 逐個拆。
