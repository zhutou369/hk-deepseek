## 測試背景與版本

上週升級後，我拿 DeepSeek 做了一輪「自然語言轉 SQL」的實測。用的是 **DeepSeek-V3** 模型（2024 年 12 月發布，API 版本號以 platform.deepseek.com 文檔為準），網頁版和 API 各測一輪。場景貼近香港中小企：訂單查詢、庫存盤點、客戶分段。我不追求學術基準，只看「寫出來的語句能不能直接跑」。

先說結論：簡單查詢很穩，多表關聯要盯緊，日期和 NULL 是兩大坑。以下是我實際操作的步驟和觀察。

## 我怎麼測：三步操作流程

### 第一步：用清楚的中文描述需求

我打開 [DeepSeek 網頁版](https://chat.deepseek.com)，貼上提示詞：「有一張 orders 表（order_id, customer_id, order_date, total_amount）和 customers 表（customer_id, name, city）。請寫一條 SQL，找出 2024 年 1 月之後、來自香港的客戶，按總金額由高到低排序，只取前 10 筆。」

關鍵是**把表結構和欄位寫清楚**。我試過只寫「幫我查香港客戶的訂單」，模型會假設欄位名，跑起來就報錯。提示詞的基本功可以參考站內 [DeepSeek 提示詞入門](/posts/deepseek-prompt-basics/)。

### 第二步：檢查生成的 SQL 並手動修正

模型給出類似：

```sql
SELECT c.name, SUM(o.total_amount) AS total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE c.city = 'Hong Kong' AND o.order_date >= '2024-01-01'
GROUP BY c.name
ORDER BY total DESC
LIMIT 10;
```

這條基本可用。但我發現兩個細節：第一，`city` 的值我實際存的是「Hong Kong」還是「香港」，模型不會知道，要自己對；第二，`order_date` 若是字串格式，比較時可能出問題。我手動改成 `o.order_date >= DATE '2024-01-01'` 更穩。

### 第三步：用 API 批量測試並記錄錯誤

我寫了一個小腳本，把 20 條自然語言需求逐條送進 API，記錄生成結果和執行報錯。這裡要注意 API 的速率限制和重試邏輯，站內 [DeepSeek API 重試指南](/posts/deepseek-api-retry-guide/) 有講。測試時遇到 429 報錯，按文檔退避重試即可。

20 條裡，13 條一次跑通，4 條小改後跑通，3 條需要重寫。錯誤集中在：多表 JOIN 別名衝突、日期格式、以及 `NULL` 處理（例如 `SUM` 遇到空值）。

## 常見問題

**Q1：DeepSeek 生成的 SQL 可以直接上生產環境嗎？**
不建議。先在校驗環境跑，確認欄位名、資料類型和邊界條件。涉及刪除或更新語句時，務必加 `WHERE` 並人工審核。

**Q2：為什麼模型有時把日期寫成字串？**
模型不知道你資料庫的實際類型。最好在提示詞裡註明「order_date 是 DATE 類型」，或生成後手動轉換。不同資料庫的日期函數也有差異，以官方文檔為準。

**Q3：香港常用嘅中文欄位名，模型識唔識？**
我試過用中文欄位名（例如「客戶編號」），模型能生成，但建議加引號或反引號，避免資料庫保留字衝突。

**Q4：用 API 定網頁版好？**
批量測試用 API 方便記錄，日常查詢網頁版夠用。API 的 Key 和額度管理可看 [DeepSeek API Key 與限制說明](/posts/deepseek-api-key-and-limits/)。

**Q5：如果公司唔想資料出街，有冇本地方案？**
可以考慮用 Ollama 本地跑開源模型，站內 [DeepSeek Ollama 本地安裝](/posts/deepseek-ollama-local-setup/) 有步驟。不過本地模型能力與線上版有差異，以官方文檔為準。

## 給香港中小企的實用建議

我測試時發現，最有效的做法是「先給表結構，再給業務規則」。例如明確寫「金額單位是港幣，NULL 當 0 處理」，生成質量會明顯提升。另外，把常用查詢存成模板，讓模型基於模板改寫，比從零生成穩定。

還有一點：數據安全要留意。如果 SQL 涉及客戶個人資料，盡量在本地或私有環境處理，不要直接把敏感資料貼進公開對話。
