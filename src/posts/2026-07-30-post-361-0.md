## 防範 SQL 注入：參數化查詢是王道

DeepSeek API 本身主要處理語言模型請求，它不會直接跑你的 SQL 查詢。但是，如果你的程序在把用戶輸入餵給 DeepSeek API *之前*，需要跟數據庫打交道（比如查用戶設置、歷史記錄啥的），那 SQL 注入就成了個要命的隱患！攻擊者就是想辦法在輸入框裡塞惡意 SQL 語句，讓數據庫執行它不想執行的操作。

**步驟 1：參數化查詢或 ORM 走起來！**

最牛的防禦辦法，就是用『參數化查詢』(Parameterized Queries) 或者『對象關係映射』(ORM) 框架。原理很簡單：它倆把查詢語句和參數分開處理，數據庫會把傳進來的東西都當成純粹的數據，壓根兒不把它當成能執行的 SQL 代碼。這從根子上就把注入的路子給堵死了。

舉個栗子，用 Python 的 `psycopg2` 連 PostgreSQL，應該這麼幹：

```python
# 反面教材：這樣寫，分分鐘被 SQL 注入！
# user_input = "' OR '1'='1"; DROP TABLE users; --"
# cursor.execute(f"SELECT * FROM users WHERE username = '{user_input}'")

# 正確姿勢：用參數化查詢
user_input = "some_user_input"
cursor.execute("SELECT * FROM users WHERE username = %s", (user_input,))
```

## 應對惡意參數竄改：輸入驗證與白名單機制

除了 SQL 注入，惡意參數竄改也是 DeepSeek API 應用常遇到的坑。攻擊者會改動發送給 API 的請求參數，企圖繞過業務邏輯、獲取未授權數據或者觸發異常行為。比如，修改用戶 ID、訂單狀態、價格等。這方面，我們要嚴格把控輸入數據的『合法性』。

**步驟 2：嚴格執行輸入驗證**

任何來自用戶端的輸入，不論是表單數據、URL 參數還是 JSON 請求體，都必須進行嚴格的驗證。確認數據類型、格式、長度、取值範圍等是否符合預期。比如，如果一個參數應該是數字，就不要接受字符串；如果一個 ID 應該是 UUID 格式，就只接受 UUID。這一步非常關鍵，能過濾掉大量無效和惡意的輸入。

```python
# 簡單的 Python 輸入驗證示例
import re

def validate_user_id(user_id_str):
    if not isinstance(user_id_str, str):
        return False
    # 假設用戶 ID 必須是純數字且長度為 6 位
    return bool(re.fullmatch(r'\d{6}', user_id_str))

# 使用前驗證
user_input_id = "123456" # 假設從請求中獲取
if validate_user_id(user_input_id):
    # 只有驗證通過才繼續處理
    # pass user_input_id to DeepSeek API or database query
    print(f"用戶 ID {user_input_id} 合法，可以處理")
else:
    # 返回錯誤信息
    print("用戶 ID 無效！")
    # abort(400, description="Invalid User ID")
```

**步驟 3：實施白名單機制**

當輸入參數的取值範圍有限且已知時，白名單機制比黑名單更安全有效。黑名單是禁止已知的不良輸入，但攻擊者總能找到新花樣；白名單則是只允許預先定義好的安全輸入，任何不在白名單裡面的，一律拒絕。比如，你讓用戶選擇一個操作類型（如 '查詢', '編輯', '刪除'），就只允許這三個值，其他值全部拒絕。這招對像下拉菜單、固定選項之類的場景特別好用。關於更安全的白名單實踐，你可以參考這篇 [API 安全設計的白名單與黑名單策略](/posts/api-whitelist-blacklist-strategy/)。

## 其他加強防護小貼士

除了上面那些核心防禦，還有幾招可以讓你的 DeepSeek API 應用更堅固：

*   **最小權限原則：** 給 API 金鑰或者應用程序配置權限時，只賦予它完成任務所需的最少權限，不多給一分。這樣即使金鑰洩漏，也能把損失降到最低。
*   **日誌記錄與監控：** 做好詳細的日誌記錄，監控可疑的請求模式或者錯誤信息。一旦發現異常，能及時響應。比如，我自己在測試時發現，有時短時間內出現大量無效參數請求，這就得警惕了。
*   **安全標頭和 CORS 配置：** 確保 HTTP 響應頭有正確的安全配置（例如 Content-Security-Policy, X-Frame-Options 等），並且跨域資源共享 (CORS) 策略配置得當，只允許信任的來源訪問。這能有效防止一些前端攻擊手段。
*   **限流與熔斷：** 對於 DeepSeek API 的調用，可以實施限流策略，防止短時間內被惡意刷爆。如果後端服務壓力過大或出現故障，可以採用熔斷機制，避免整個系統崩潰。這在 [高併發 API 設計中的限流熔斷策略](/posts/high-concurrency-api-rate-limiting-circuit-breaking/) 裡有詳細介紹。

## 常見問題

**Q1：DeepSeek API 本身安全嗎？我還需要做這些嗎？**

A1：DeepSeek API 服務端在安全方面投入了大量精力，這點完全可以放心。但我們討論的是應用層面的安全。就好比銀行大門很結實，但你個人錢包也要看好。用戶輸入經由你的應用程式，再傳遞給 DeepSeek API，這個環節就是我們需要重點防護的。這些步驟是為了加固你的應用程序，防止它成為攻擊的入口。

**Q2：我的應用程序很小，流量也不大，有必要這麼麻煩嗎？**

A2：當然有必要！無論應用大小，一旦涉及用戶數據或系統功能，安全都是零容忍。攻擊者可不管你流量大小，有漏洞就會利用。早點做好安全防護，勝過事後補救，省心也省力。

**Q3：參數化查詢是不是隻針對 SQL 數據庫？DeepSeek API 是語言模型，沒有數據庫啊？**

A3：你說得對，DeepSeek API 本身不執行 SQL。這裡的參數化查詢，是指你的應用程序在『發送數據給 DeepSeek API 之前』，如果需要從你自己的數據庫裡撈數據，或者把 DeepSeek API 的結果存入數據庫，這時就必須用參數化查詢來跟自己的數據庫互動。它保護的是你的應用後端數據庫，而不是 DeepSeek API 服務端。至於 DeepSeek API 請求本身的參數安全，那主要靠『輸入驗證』和『白名單機制』來搞定，也就是我們上面提到的步驟 2 和步驟 3。

**Q4：DeepSeek API 有沒有自帶的防注入或參數篡改功能？**

A4：DeepSeek API 服務端確實會對輸入進行一定程度的檢查和消毒，以確保服務自身的穩定和安全。但這並不能替代你應用層面的安全防護。因為攻擊者是衝著你的應用邏輯來的，而不是直接攻擊 DeepSeek 的後端。你的應用是第一道防線，必須自己守好。"
