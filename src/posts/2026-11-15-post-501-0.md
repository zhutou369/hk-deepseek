## 先確認版本與環境

我測試時的環境是：Python 3.11、`requests` 2.31.0、DeepSeek API 的 chat completions 串流端點，日期為 2025 年 3 月。如果你用的是其他 SDK 或版本，具體行為請以官方文檔為準。

串流模式下，客戶端和伺服器之間走的是 Server-Sent Events（SSE）。連線被中間裝置切斷、心跳沒送達、代理伺服器緩衝了數據，都會讓你看起來像「API 壞了」。但多數時候問題在網絡鏈路或客戶端設定。

## 三步排查串流失敗

### 第一步：確認是否 SSE 中斷

先看錯誤碼和訊息。如果收到 `requests.exceptions.ChunkedEncodingError` 或 `ConnectionResetError`，大概率是連線被中途切斷。我當時用 `curl` 直接測，發現串流回傳到一半就停，但非串流請求正常。這表示問題出在長連線，而不是認證或配額。

檢查方法：

```bash
curl -N -X POST https://api.deepseek.com/chat/completions \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-chat","stream":true,"messages":[{"role":"user","content":"test"}]}'
```

如果 `curl` 也斷，換網絡環境再試。若只在公司網絡斷，問題可能在代理。

### 第二步：檢查心跳與超時設定

SSE 連線需要定期心跳來維持。客戶端如果設定了過短的讀取超時，例如 10 秒，就可能誤判為斷線。我測試時把 `timeout` 從 10 秒調到 60 秒，中斷頻率明顯下降。

另外，有些代理伺服器會緩衝 SSE 數據，導致心跳無法即時送達。你可以在請求標頭加入 `Cache-Control: no-cache` 和 `Connection: keep-alive`，並確認代理沒有啟用回應緩衝。

如果使用 Nginx 反向代理，記得關閉 `proxy_buffering`，並適度調高 `proxy_read_timeout`。具體參數以你的代理版本為準。

### 第三步：代理伺服器設定排查

中小企網絡常經過防火牆或代理。我實測時發現，公司代理會把超過 30 秒的閒置連線切斷，而 SSE 心跳間隔若大於這個值就會斷線。解決方式有兩個：一是請網絡管理員調高連線閒置超時；二是在客戶端加入應用層心跳，例如每 15 秒發送一個空註釋行。

如果你用 Python 的 `requests`，可以這樣寫：

```python
import requests

with requests.post(url, headers=headers, json=payload, stream=True, timeout=(10, 60)) as r:
    for line in r.iter_lines(decode_unicode=True):
        if line:
            print(line)
```

注意 `timeout` 設為 tuple，分別控制連線和讀取超時。讀取超時要留夠餘量，避免心跳間隔較長時被誤斷。

## 常見問題

**問：串流中斷後需要重試嗎？**

答：可以，但建議只重試未完成的部份。若中斷頻繁，先排查網絡和代理，而不是盲目重試。重試策略可參考站內的重試指南。

**問：為什麼非串流請求正常，串流卻一直斷？**

答：非串流請求是短連線，完成即斷；串流是長連線，更容易受代理緩衝、防火牆閒置超時影響。這是我測試時最常見的原因。

**問：心跳超時要設多少？**

答：沒有統一答案，取決於你的代理和網絡設備。一般建議讀取超時設 60 秒以上，並確認代理的閒置超時大於心跳間隔。以官方文檔為準。

**問：用 Ollama 本地模型會有同樣問題嗎？**

答：本地模型不經過外部代理，但如果你透過反向代理暴露服務，仍可能遇到 SSE 緩衝問題。設定思路相同。

**問：API Key 權限會影響串流嗎？**

答：一般不會，但若 Key 有速率限制或餘額不足，伺服器可能中斷連線。先確認帳戶狀態和配額，可參考 API Key 與限制的說明。

排查時保持耐心，先從最外層的網絡和代理開始，再往客戶端設定查。多數串流中斷不是模型問題，而是連線維持的細節沒調好。
