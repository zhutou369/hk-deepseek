## 點解我會試用 DeepSeek 寫正則

上星期公司要從一堆混亂嘅 log 檔抽出香港電話號碼，我順手開咗個正則表達式練習。以往我會自己砌，但今次想試下用 DeepSeek 幫手。結果發現，佢唔止生成到 pattern，仲可以逐段解釋畀我聽，對於我呢啲成日忘記 `\d` 同 `\w` 分別嘅人嚟講，幾實用。

我測試嘅版本係 DeepSeek-V3，日期係 2025 年 6 月 18 日，透過網頁版 [chat.deepseek.com](https://chat.deepseek.com) 使用，冇開 API。如果你用 API，就要留意 token 限制，可以參考站內嘅 [DeepSeek API key 同額度說明](/posts/deepseek-api-key-and-limits/)。另外，我上週升級咗本地 Ollama 版本，試過用離線模型跑正則生成，速度慢啲但私隱好啲，設定方法喺 [Ollama 本地部署教學](/posts/deepseek-ollama-local-setup/) 有講。

## 三步操作：由零到有正則

**第一步：用自然語言描述需求**

我打咗呢句：「幫我寫一個正則表達式，匹配香港手機號碼，格式係 8 位數字，開頭係 5、6、7 或 9，可以接受有空格或者冇空格。」DeepSeek 好快就回咗個 pattern：`^[5679]\d{7}$`，仲問我要唔要埋 `+852` 前綴。

**第二步：要求解讀同測試案例**

我唔想死記，所以叫佢逐個 token 解釋。佢回覆：`^` 係開頭，`[5679]` 係第一個字元只可以係呢四個數，`\d{7}` 係之後七個數字，`$` 係結尾。跟住我請佢畀幾個測試字串，佢列咗「91234567」（匹配）、「5123456」（唔匹配）同「9123 4567」（唔匹配，因為有空格）。我實測發現，如果號碼中間有空格，就要改為 `^[5679]\d{3}\s?\d{4}$`，呢點佢冇主動提，要我自己追問。

**第三步：用報錯訊息反向優化**

我喺 Python 用 `re` 模組試，遇到 `re.error: bad character range`，直接貼返個錯誤畀 DeepSeek。佢解釋係因為我喺字元類別入面寫咗 `[5-9-]` 呢種模糊範圍，建議我明確寫 `[5679]`。呢個反向診斷過程，比起自己上網搵答案快好多。如果你用 API 遇到 error code，可以睇 [API 重試機制指南](/posts/deepseek-api-retry-guide/) 了解多啲。

## 常見問題

**Q1：DeepSeek 生成嘅正則一定啱嗎？**

唔一定。我試過叫佢匹配電郵，佢出咗個簡化版，唔支援國際化域名。所以最好自己用測試案例驗證，或者要求佢列出已知限制。

**Q2：使唔使畀錢？**

網頁版免費，API 就要睇官方定價，以官方文檔為準。

**Q3：可唔可以生成埋解釋？**

可以，但你要明確咁問：「逐個 token 解釋」。如果唔問，佢通常只會畀 pattern。

**Q4：支援邊種語言嘅正則？**

佢預設會用通用語法，但你可以指定「用 Python re 模組」或者「用 JavaScript 正則」。我測試時發現，指定語言之後，佢會避開一啲跨語言唔支援嘅寫法。

**Q5：如果生成結果太複雜點算？**

可以叫佢「簡化，犧牲少少準確度」，或者分拆成多個步驟匹配。另外，用 [Prompt 基礎技巧](/posts/deepseek-prompt-basics/) 入面嘅「角色設定」方法，叫佢做「資深正則專家」，出嚟嘅結果會更貼近實戰。

## 我嘅結論：啱用定唔啱用？

對於中小企嚟講，DeepSeek 寫正則係一個幾好嘅起點，尤其係解釋部分，幫我省返唔少查文檔時間。但千祈唔好當佢係絕對正確，一定要自己跑測試。我而家嘅習慣係：生成、解讀、測試、再優化，四個步驟走唔甩。如果你都想試，記住用自然語言描述清楚邊界條件，咁佢先會畀到啱你嘅答案。
