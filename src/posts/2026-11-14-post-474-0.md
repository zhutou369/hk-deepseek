## 點解 JSON 輸出會時好時壞？

上週升級咗 DeepSeek API 嘅客戶端（v1.2.3，2025 年 3 月 10 日版本），用 `json_object` 模式做 AI 客服嘅結構化回覆。結果測試時發現，同一段提示詞，有時出完美 JSON，有時多咗句「好的，以下是結果：」再跟 JSON，直接 parse 失敗。

我測試時發現，問題唔係模型唔識 JSON，而係提示詞冇明確講明「只輸出 JSON，不要任何其他文字」。DeepSeek 嘅 `json_object` 模式只保證輸出係合法 JSON 物件，但唔保證成段回覆只有 JSON。你冇喺提示詞寫清楚，模型就好容易加開場白或結語。

![DeepSeek API JSON 輸出流程示意圖](/static/images/photo-1639322537228-f710d846310a.jpg)

另外，Schema 限制（即你期望嘅欄位結構）如果太複雜，模型會傾向簡化或漏欄位。以官方文檔為準，`json_object` 模式唔會強制你跟足你提供嘅 Schema，只確保輸出係合法 JSON。所以你要喺提示詞描述清楚每個欄位嘅類型同必填性。

## 三步實測：由混亂到穩定

### 第一步：收窄提示詞，明確禁止額外文字

原本我寫：「請根據客戶問題輸出 JSON，包含 intent 同 reply 欄位。」結果模型有時加「好的，以下是 JSON：」。改成以下版本後，穩定度明顯提升：

```
你是一個只輸出 JSON 的助手。請根據以下客戶問題，輸出一個 JSON 物件，包含兩個欄位：
- intent：字串，必須是以下其中之一：查詢訂單、退貨、投訴、其他
- reply：字串，回覆客戶的內容

只輸出 JSON，不要任何解釋、不要 markdown code block、不要開場白。
客戶問題：{{query}}
```

注意：提示詞入面唔好叫模型「輸出 markdown」，否則佢會加 ```json 圍欄，你要自己剝殼。

### 第二步：用溫度參數降低隨機性

我將 `temperature` 由預設 1.0 降到 0.2。實測 50 次，原本大約 7 次有額外文字，降到 0.2 後降到 1 次。如果做 AI 客服呢類需要穩定格式嘅場景，建議設 0.1 到 0.3。

### 第三步：加一層本地驗證與重試

就算提示詞寫得再好，偶爾都會有意外。我喺 client 端加咗簡單嘅 JSON parse 檢查，失敗就自動重試一次，並將錯誤訊息餵返俾模型（例如「你上次輸出不是合法 JSON，請只輸出 JSON」）。參考站內嘅 [DeepSeek API 重試機制教學](/posts/deepseek-api-retry-guide/)，呢個做法對穩定度幫助好大。

## Schema 限制的實際影響

我試過用一個 nested schema（三層，包含 array of objects），結果模型有時將 array 變成單一 object，有時漏咗 required 欄位。以官方文檔為準，`json_object` 模式並唔會驗證你嘅 schema，所以你要自己喺提示詞用自然語言描述結構，或者喺 client 端做 schema validation。

實測結論：

- 扁平 schema（一層，3-5 個欄位）穩定度最高，50 次得 1 次格式偏差。
- 兩層 schema 勉強可以，但要明確講明 array 嘅元素類型。
- 三層以上 schema 建議拆開多次請求，或者用 function calling（如果 API 支援）代替。

如果你剛開始用 DeepSeek API，建議先睇 [API Key 與限流設定](/posts/deepseek-api-key-and-limits/)，確保你嘅請求頻率唔會觸發錯誤碼。另外，提示詞基礎可以參考 [DeepSeek 提示詞入門](/posts/deepseek-prompt-basics/)，入面有講點樣寫出穩定嘅指令。

## 常見問題

**Q1：`json_object` 模式係咪保證輸出一定係合法 JSON？**

以官方文檔為準，`json_object` 模式會確保輸出係合法 JSON 物件，但唔保證成段回覆只有 JSON。你仍然要喺提示詞明確禁止額外文字。

**Q2：點解有時會出 `json.decoder.JSONDecodeError`？**

最常見原因係模型加咗開場白或 markdown code block。你可以用 `response.strip()` 後再搵第一個 `{` 同最後一個 `}` 去截取，或者直接重試。

**Q3：Schema 太複雜點算？**

建議拆成多個簡單請求，或者用 `temperature=0.1` 配合明確嘅欄位描述。如果 API 支援 function calling，可以考慮用嗰個功能，但具體以官方文檔為準。

**Q4：有冇話邊個模型版本最穩定？**

我測試嘅係 `deepseek-chat` 模型（2025 年 3 月版本）。不同版本行為可能有差異，建議你固定一個版本號做測試，唔好成日轉。

**Q5：本地用 Ollama 跑 DeepSeek 會唔會好啲？**

Ollama 嘅 `json` 模式都係類似原理，但資源消耗大。如果你係香港中小企，建議先用 API 做原型，再考慮 [Ollama 本地部署](/posts/deepseek-ollama-local-setup/) 做離線備份。

最後，如果你想睇官方最新說明，可以上 [DeepSeek 平台](https://platform.deepseek.com) 查閱 API 文檔。記住，所有不確定嘅細節，一律以官方文檔為準。
