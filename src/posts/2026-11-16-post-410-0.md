上周三凌晨，我正在跑一个自动化工作流，突然收到 DeepSeek API 返回 `429 Too Many Requests`，然后余额直接归零。那一刻我才想起来：免费额度和充值额度分开算，而我忘了设余额提醒。

如果你也遇到过类似情况，别急着改架构。下面是我实测可行的临时做法，重点是“先顶上”，不是长期方案。

## 为什么会撞上额度用完

DeepSeek API 的额度分几种：注册赠送、充值余额，还有不同时段的费率。按官方文档，`429` 通常表示请求过密或余额不足，`402` 多半是余额问题。我测试时发现，如果工作流用固定间隔重试，很容易把剩余额度烧得更快。

![DeepSeek API 多Key轮换架构示意图](/static/images/photo-1508873535684-277a3cbcc4e8.jpg)

另一个常见原因：你以为在用一把 key，但环境变量里还有旧 key 没清掉，请求分散到几个不同账户，其中一个先耗尽了。

## 多Key轮换：我的实测步骤

这招适合手上有两三个 DeepSeek 账户（比如公司和个人的分开）。原则是：把请求平均分配到多条金钥，某条报错时自动跳下一条。

### 步骤一：整理金钥清单

打开终端，用环境变量或 `.env` 文件管理金钥，别写死在代码里。例如：

```bash
export DEEPSEEK_KEYS="sk-aaa,sk-bbb,sk-ccc"
```

我习惯用逗号分隔，再在程序里 split 成数组。记得每条金钥都要去 [DeepSeek 平台](https://platform.deepseek.com) 确认有效，顺便看清各自余额。

### 步骤二：写个简单轮换逻辑

不用搞太复杂，一个 round-robin 加错误重试就够了。伪代码大概这样：

```python
keys = os.getenv("DEEPSEEK_KEYS").split(",")
index = 0
for attempt in range(len(keys)):
    key = keys[index % len(keys)]
    resp = call_deepseek(key, payload)
    if resp.status_code == 200:
        break
    if resp.status_code in (429, 402):
        index += 1
        continue
    raise Exception(resp.text)
```

关键是：遇到 `429` 或 `402` 才跳 key，其他错误（比如 `400`）别乱跳，否则只会浪费时间。

### 步骤三：加入冷却和日志

每条金钥失败后，至少等 60 秒再试，同时把失败原因写进 log。我试过连续重试同一把耗尽的 key，结果触发更长的冷却期，反而拖慢整个流程。

如果你需要更完整的重试策略，可以看站内的 [DeepSeek API 重试机制实战](/posts/deepseek-api-retry-guide/)，里面讲了怎样区分暂时性错误和永久性错误。

## 供应商切换：中断时的临时方案

当所有金钥都用尽，或者你根本只有一个账户，就得考虑换供应商。这里说的“供应商”包括两类：其他云端 API 平台，和本地模型。

![DeepSeek 供应商切换流程图](/static/images/photo-1513530534585-c7b1394c6d51.jpg)

### 云端替代：OpenRouter 等聚合平台

如果你的工作流用 OpenAI 兼容格式，可以短时间内把 `base_url` 指去其他平台。拿 OpenRouter 来说，它提供 DeepSeek 模型的路由，但价格和可用性以该平台官网为准。切换时记得改 API key 和 model name，别直接复制旧配置。

### 本地替代：Ollama 跑小模型

如果只是测试或非关键任务，我会用 Ollama 在本机跑个小模型顶着。设好后，把 `base_url` 改成 `http://localhost:11434/v1`，就能用类似 OpenAI 的方式调用。具体安装步骤可以看 [DeepSeek Ollama 本地安装教程](/posts/deepseek-ollama-local-setup/)，我上次跟着做大概十分钟搞定。

注意：本地模型的输出质量和延迟跟云端 API 有明显差距，只适合临时顶替，别当长期方案。

## 常见问题

**Q1：多Key轮换会不会被封号？**

按官方公开信息，DeepSeek 没有明确禁止多账户，但如果你用同一身份证明大量注册，有可能触发风控。建议只在合理范围内使用，比如公司和个人的账户分开。

**Q2：怎么知道额度快用完了？**

登录 platform.deepseek.com 的用量页面，设置余额提醒。我试过在余额低于 10% 时收到电邮通知，但不肯定是不是所有账户都有，以官方文档为准。

**Q3：切换供应商后，prompt 要改吗？**

多数情况要微调。不同模型对 system prompt 的敏感度不同，建议先看 [DeepSeek Prompt 基础教学](/posts/deepseek-prompt-basics/)，再用少量测试案例对比输出。

**Q4：429 和 402 有什么区别？**

`429` 多半是请求频率过高或并发太多；`402` 通常跟付费余额有关。两者都可能出现在额度耗尽时，但处理方式不完全一样。

**Q5：有办法完全避免额度用完吗？**

没有，但可以降低影响。设预算提醒、用多个供应商做 fallback、把非关键任务改为本地模型，都是我实测有效的做法。

最后提醒一句：以上方案只是临时顶替，长远还是要监控用量和调整工作流。如果你刚上手 DeepSeek API，建议先看 [API Key 与额度说明](/posts/deepseek-api-key-and-limits/)，搞清楚收费模式再进场。
