## 中轉站是啥原理？

說白了，DeepSeek API 中轉站就是讓你的應用不再直接連 DeepSeek 官方那麼遠，而是先連我們 Vultr 東京的伺服器。伺服器再幫你把請求轉給 DeepSeek，拿到結果後返回。這套系統要考慮『高可用』和『多路由容災』，這樣服務才夠穩、不斷線。我測試這套方案是基於 Nginx 1.22.1 版本，時間是 2024 年 5 月底，確定沒問題！

### 第一步：Vultr 伺服器選購與開通

上 Vultr 官網（`https://www.vultr.com/`）註冊個賬號，開一台新雲伺服器。記得選『Tokyo (JP)』機房，香港連過去延遲最低！操作系統推薦 Ubuntu 22.04 LTS，又穩又好用。配置方面，最低配（1 vCPU, 1GB RAM）初期絕對夠用，流量大了再說。搞定後，把伺服器 IP 和 root 密碼記下來。

### 第二步：Nginx 代理與負載均衡設置

我們用 Nginx 做反向代理。登錄 Vultr 伺服器，先更新系統，再安裝 Nginx：

```bash
sudo apt update
sudo apt upgrade -y
sudo apt install nginx -y
```

Nginx 裝好後，編輯默認配置文件 `/etc/nginx/sites-available/default`：

```bash
sudo nano /etc/nginx/sites-available/default
```

把 `location /` 區塊改成下面這樣，以 DeepSeek 聊天 API 為例：

```nginx
server {
    listen 80;
    server_name your_domain.com your_server_ip; # 記得換成你自己的域名或 IP

    location / {
        proxy_pass https://api.deepseek.com/v1/chat/completions; # DeepSeek 官方 API 端點
        proxy_set_header Host api.deepseek.com;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 容災和重試配置
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
        proxy_buffers 16 4k;
        proxy_buffer_size 8k;
        proxy_busy_buffers_size 16k;
        proxy_ignore_headers Cache-Control Expires Set-Cookie;
        proxy_http_version 1.1;
        proxy_set_header Connection ""; # 保持連線

        # 上游服務器掛了？Nginx 自動重試！
        proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
        proxy_next_upstream_tries 3; # 最多重試3次
        proxy_next_upstream_timeout 10s; # 重試超時時間
    }
}
```

這個配置會把 `/` 路徑請求轉發到 DeepSeek 聊天 API。其中 `proxy_next_upstream` 能讓 Nginx 在 DeepSeek API 臨時出問題時自動重試，給單個中轉站提供基本容錯能力。要代理其他 DeepSeek API，改 `proxy_pass` 地址就行。配置好了，保存然後重啟 Nginx：

```bash
sudo nginx -t # 檢查語法
sudo systemctl reload nginx
```

### 第三步：域名設置與客戶端容災

需要個域名方便訪問，解析到你 Vultr 伺服器 IP 上（加 A 記錄）。

真正『多路由容災』得這樣：在 Vultr 東京多開幾台伺服器，每台都配 Nginx，各自有公網 IP。然後用 Cloudflare DNS 或 Route 53 這種支持健康檢查和智能 DNS 的服務管理。萬一某個中轉站掛了，DNS 會自動把流量切到其他正常的伺服器，你的應用幾乎感覺不到，還是持續向域名發請求就得了，是不是很酷？

你的應用調用中轉站時，自己也最好做個重試機制。客戶端再加一道保險，總是個好習慣。詳細玩法，看這篇 [DeepSeek API 請求重試指南](/posts/deepseek-api-retry-guide/)。

## 服務穩定不穩定，全靠監控和更新

中轉站搭好可不能放著不管！持續監控運行狀態很重要。可以用 UptimeRobot 監控伺服器，或上 Prometheus + Grafana 收集請求量、響應時間、錯誤率。平時多翻 Nginx 日誌也能早點發現問題。

## 常見問題 Q&A

### Q1: 為啥選 Vultr 東京，香港不行嗎？

香港機房雖近，但考慮線路質量、穩定性和性價比，Vultr 東京連 DeepSeek API 時表現通常更好，特別能避開線路擁堵。對香港用戶來說，兩者延遲基本沒差，甚至東京更穩當些。

### Q2: 自己搭中轉站，費用咋控制？

Vultr 最便宜的伺服器每月費用不高，中小企能接受。主要費用就是伺服器租用和域名。合理規劃伺服器數量（剛開始一台就夠），盯著流量看，就能把成本控制好。流量大了再升級或加機器。

### Q3: API 金鑰怎麼保證安全？

DeepSeek API 金鑰只存中轉站伺服器上，絕不能讓客戶端直接接觸！Nginx 代理轉發請求時，會把客戶端認證信息換成你伺服器配好的金鑰。為了更安全，務必給中轉站啟用 HTTPS (SSL/TLS) 加密通信。金鑰管理不懂的，看這篇 [DeepSeek API 金鑰及使用限制](/posts/deepseek-api-key-and-limits/)。

### Q4: 萬一 DeepSeek 官方 API 接口變了咋辦？

DeepSeek 畢竟是大廠，API 一般都會兼容舊版本。就算有大更新，也會提前發公告或給過渡期。所以，你得定期關注 DeepSeek 開發者文檔，及時調整配置。如果 API 地址或請求格式變了，可能要更新 Nginx 配置來適應。
