## 為什麼溫度參數值得花時間調

DeepSeek 的 temperature 值控制輸出隨機程度。數值越低，模型越傾向選用概率最高的詞；數值越高，選詞越分散。這件事在翻譯和寫程式時特別明顯。

我上週升級到 DeepSeek-V3 的 API 版本（2025 年 5 月的模型快照），把同一批任務分別用 0.2、0.7、1.3 跑了一次。結果差別不是「好一點」那麼簡單，而是整個輸出風格都變了。翻譯用 1.3 的時候，模型開始加入原文沒有的修飾；寫程式用 1.3 的時候，它會偶爾插入一段看似合理但根本編譯不過的邏輯。

## 三種任務的實測設定

**寫作類任務：0.7 到 0.9。** 我用來寫博客草稿和產品說明，0.7 出來的句子比較自然，不會每段都用同一種句式開頭。低於 0.5 會變得乾巴巴，像在讀說明書。

**翻譯任務：0.2 到 0.4。** 這個區間最穩。我測試時發現，超過 0.6 之後，模型開始「意譯」，中文成語會被換成英文裡意思接近但語氣不同的表達。如果你的場景是法律或技術文件，直接壓到 0.2，配合提示詞要求「逐句對照」，效果最好。提示詞寫法可以參考[提示詞基礎教學](/posts/deepseek-prompt-basics/)。

**寫程式：0.3 到 0.5。** 這個區間能保留一點變化，讓模型在命名和註釋上有彈性，但不會亂造 API。低於 0.2 有時候會卡在同一個錯誤的解法裡出不來，反而更麻煩。

如果是通過 Ollama 跑本地版本，參數名稱和範圍以官方文檔為準，不同量化版本的行為可能略有差異，可以看[本地部署教學](/posts/deepseek-ollama-local-setup/)先確認環境。

## 具體操作步驟

### 步驟一：先固定一個基準

打開 API 調用或網頁版設定，把 temperature 設成 0.7，其他參數保持默認。用一段你熟悉的素材跑一次，記錄輸出裡你滿意和不滿意的點。這一步是為了建立對照組，不然你後面調了也不知道變好還是變壞。

### 步驟二：按任務分檔調低

翻譯和程式碼直接降到 0.3 附近，寫作保持在 0.7 到 0.8。每次只改一個參數，跑三到五個樣本。我在測試翻譯時，同一段英文用 0.2 和 0.4 各跑三次，0.4 的那組有一次把被動語態改成了主動，意思沒變但語氣偏了。這種細節只有對照才看得出來。

![DeepSeek API 參數設定介面示意](/static/images/photo-1496065187959-7f07b8353c55.jpg)

### 步驟三：觀察錯誤率再微調

寫程式的時候，把每次輸出的報錯碼記下來。如果同一類報錯反覆出現，先把溫度降到 0.3 再試；如果輸出太死板、命名全是 `data1`、`data2`，就升到 0.5。調完之後建議做一輪回歸測試，確認沒有引入新的問題。API 調用如果遇到限流或超時，可以配合[重試機制說明](/posts/deepseek-api-retry-guide/)處理。

## 常見問題

**溫度設 0 是不是最準確？** 不一定。0 會讓輸出完全確定，但翻譯時可能過於直譯，程式碼也容易卡在同一個思路。實務上留一點隨機性反而更好。

**網頁版和 API 的溫度行為一樣嗎？** 網頁版不一定開放這個參數，具體以官方介面顯示為準。要精細控制還是走 API。

**為什麼同一組參數兩次結果差很多？** 除了 temperature，還有其他採樣參數和模型版本在影響。2025 年 5 月的模型快照和更早版本的行為就可能不同，建議固定版本號再比較。

**翻譯長文要分段調嗎？** 可以。長文前段用 0.3 建立術語表，後段沿用同一組術語，溫度保持一致，避免前後用詞不統一。

**寫程式時溫度低還是高比較安全？** 偏低比較安全，但別壓到 0。0.3 到 0.4 是我目前比較順手的區間，具體還是看你用的語言和框架。
