## 為什麼用 vLLM 跑 DeepSeek？

上週升級咗部工作站，用 vLLM 0.6.3 配 DeepSeek-V2-Lite 跑本地推理，發現佢嘅 PagedAttention 同連續批處理（continuous batching）真係幫到手。以前用 Hugging Face transformers 跑，單張 24GB 顯示卡，同時開 4 個請求就開始排队，吞吐量跌到得 3-4 tokens/s。轉用 vLLM 之後，同樣硬件，併發 8 個請求都頂得住，平均吞吐量升到 15 tokens/s 左右。

不過默認設定唔係萬能。如果你部機嘅顯示卡記憶體唔夠大，或者請求長短差異好大，vLLM 嘅默認參數可能會浪費資源。以下係我實測後覺得最值得調嘅幾步。

## 第一步：安裝與版本確認

先用 pip 裝 vLLM，建議喺虛擬環境入面做，避免同其他套件衝突。

```bash
python -m venv vllm-env
source vllm-env/bin/activate
pip install vllm==0.6.3
```

裝完之後，用 `vllm --version` 確認版本。我試過用 0.6.2 同 0.6.3 對比，0.6.3 喺處理長上下文時穩定啲，所以建議至少用 0.6.3 或以上。

![vLLM 與 DeepSeek 本地部署終端畫面](/static/images/photo-1607604276583-eef5d076aa5f.jpg)

## 第二步：啟動參數這樣調

啟動 vLLM 時，有幾個參數直接影響吞吐量：

1. `--max-model-len`：設定模型最大上下文長度。DeepSeek-V2-Lite 預設係 4096，如果你嘅請求通常短過 2048，可以調低到 2048，咁樣可以慳返 KV cache 空間，容納更多併發請求。我測試時發現，調低之後同一張卡可以多跑 2-3 個併發。
2. `--gpu-memory-utilization`：默認 0.9，即用 90% 顯示卡記憶體。如果部機仲有其他程式，可以調到 0.85 避免 OOM。但如果你係專機專用，可以試 0.95，不過要留意散熱同穩定性。
3. `--max-num-seqs`：呢個係同時處理嘅最大請求數。默認 256，但實際上要睇顯示卡記憶體。我喺 24GB 卡上設 16 到 32 之間，效果最好。設得太高反而會因為 KV cache 碎片化而拖慢。

啟動範例：

```bash
python -m vllm.entrypoints.openai.api_server \
  --model deepseek-ai/DeepSeek-V2-Lite \
  --max-model-len 2048 \
  --gpu-memory-utilization 0.9 \
  --max-num-seqs 24 \
  --port 8000
```

## 第三步：監控與壓力測試

調完參數，要用工具驗證。最簡單係用 `curl` 發送併發請求，或者用 `wrk` 配合一個簡單嘅 Python 腳本。

```bash
for i in {1..20}; do
  curl -s http://localhost:8000/v1/completions \
    -H "Content-Type: application/json" \
    -d '{"model": "deepseek-ai/DeepSeek-V2-Lite", "prompt": "你好，請介紹香港", "max_tokens": 50}' &
done
wait
```

同時開另一個終端，用 `nvidia-smi` 睇顯示卡記憶體使用率同 GPU 利用率。如果記憶體長期貼近上限，就要調低 `--max-num-seqs` 或 `--gpu-memory-utilization`。另外，vLLM 嘅日誌會顯示每秒處理嘅 tokens 數，可以喺啟動時加 `--disable-log-requests` 減少日誌干擾，但調試時建議保留。

如果想更系統化咁壓測，可以參考 [DeepSeek API 重試機制指南](/posts/deepseek-api-retry-guide/) 入面嘅思路，將重試邏輯套用到本地端點。

## 常見問題

**問：啟動時報錯 `RuntimeError: CUDA out of memory`，點算？**
答：先降低 `--gpu-memory-utilization` 到 0.8，再調低 `--max-model-len` 或 `--max-num-seqs`。如果仲係唔得，檢查係咪有其他程式佔用顯示卡記憶體。

**問：併發請求解決唔到，吞吐量冇明顯提升？**
答：可能係請求長度差異太大，導致批處理效率低。可以試設定 `--max-num-batched-tokens`（默認 2048），調低到 1024 睇吓有冇改善。另外，確保客戶端有正確處理串流回應。

**問：想用 Ollama 做前端管理，vLLM 做後端推理，得唔得？**
答：可以，但要自己寫一層轉發。Ollama 嘅 API 格式同 vLLM 嘅 OpenAI 兼容端點唔完全一樣。想了解 Ollama 本地設定，可以睇 [DeepSeek Ollama 本地部署教學](/posts/deepseek-ollama-local-setup/)。

**問：有冇推薦嘅壓力測試工具？**
答：可以用 `locust` 或 `vegeta`，兩者都支援自訂請求體。測試時記得逐漸增加併發數，觀察吞吐量同延遲嘅變化曲線。

**問：vLLM 支援 DeepSeek 邊啲模型？**
答：以官方文檔為準。目前 DeepSeek-V2 系列同 DeepSeek-V3 都有社群成功案例，但具體支援程度要睇 vLLM 版本同模型轉換腳本。建議先喺 [DeepSeek 平台](https://platform.deepseek.com) 查看模型清單，再對照 vLLM 嘅支援列表。

調優呢家嘢，冇一套參數走天涯。建議由默認設定開始，每次只改一個參數，用壓力測試記錄結果。我習慣用一個簡單嘅試算表，記低每次改動前後嘅吞吐量同延遲，慢慢就摸到部機嘅脾性。如果你對提示詞設計有興趣，可以參考 [DeepSeek 提示詞基礎教學](/posts/deepseek-prompt-basics/)，有時候優化提示詞比調參數更直接。
