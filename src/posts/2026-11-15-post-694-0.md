## 為何你的多輪對話越聊越貴

DeepSeek 的對話接口是無狀態的：每次請求你都要把整段對話歷史重新送上。這代表第 10 輪的請求，輸入 Token 是第 1 輪的好幾倍。輸入與輸出分開計價，長對話的錢主要死在輸入那一側。

我測試時發現一個很常見的寫法：把用戶每句話、模型每次回覆都原樣 append 進 list，從不清理。聊二三十輪之後，單次請求的輸入就變得相當可觀，而且模型還容易「記住」早期不相關的閒聊，回答開始飄。

所以核心只有一句：上下文不是越多越好，是越準越好。

## 三個步驟管好上下文

### 第一步：先把 system prompt 瘦身

很多人把產品說明、語氣要求、範例回答全部堆進 system。這部分每一輪都會重複計費。做法是把固定不變的短規則留在 system，長篇的知識庫問答改成按需檢索，只在相關問題出現時才注入。

一個實用寫法是在 system 裡明確何時該忘掉舊話題，例如「若用戶切換到新主題，忽略之前與新主題無關的問答」。這比事後在程式碼裡猜測有效得多。

### 第二步：用 messages 陣列裁剪，而不是整段保留

具體操作我建議這樣做：

1. 保留第一條 system 訊息，以及最近 N 輪（我實測 6 到 8 輪對話通常夠用）。
2. 中間較舊的輪次，抽成一條摘要訊息，用你自己的模型或規則生成，字數控制在數十字。
3. 每次請求前印出 `messages` 的長度與估算 Token，超過你設定的上限就觸發裁剪。

第三步是把「摘要 + 最近幾輪」組成新陣列送出，原始歷史留在本地數據庫，需要時才回查。這樣單次輸入可以穩定在可控範圍，長對話也不會突然爆量。若你想先確認請求本身的參數邊界，可以參考這篇關於 [API key 與用量限制的整理](/posts/deepseek-api-key-and-limits/)。

### 第三步：處理失敗與重試，別讓重試吃掉預算

裁剪邏輯上線後，我遇到過一次 429 報錯，原因是併發瞬間拉高。重試本身沒錯，但重試時若把整段歷史再送一次，成本會疊加。建議重試前先確認請求體沒變、加上退避等待，並區分可重試與不可重試的錯誤碼。這部分我在 [重試策略那篇](/posts/deepseek-api-retry-guide/) 踩過坑，值得先讀。

另外，如果你的場景需要離線或內網處理，把對話邏輯搬去本地跑也是省錢路線，[Ollama 本地部署的設置方式](/posts/deepseek-ollama-local-setup/) 可以配合使用。官方接口的參數說明則以 [platform.deepseek.com](https://platform.deepseek.com) 為準。

## 常見問題

**Q1：多輪對話一定要自己維護歷史嗎？**

是，接口本身不保存上下文，歷史由你的應用負責保存與裁剪。

**Q2：裁剪掉舊訊息會不會讓模型失憶？**

會損失細節，但用摘要補上關鍵結論通常足夠。涉及訂單號、金額這類硬資料，建議另行用結構化欄位保存，而不是靠對話歷史。

**Q3：怎麼估算 Token 才不會超？**

請求前先粗算字數與訊息條數，設一個軟上限，超過就裁剪。實際計費口徑以官方文檔為準。

**Q4：system prompt 很長，值得壓縮嗎？**

值得。它每輪都重複計費，壓縮一次長期有效。把可變的知識移到檢索層。

**Q5：摘要用哪個模型做比較好？**

用你手上成本較低的模型即可，摘要不需要很強的理解力。提示詞寫法可參考 [提示詞基礎那篇](/posts/deepseek-prompt-basics/)。

最後提醒一句：先量測再加功能。把每次請求的輸入長度記下來，你會發現大部分優化空間都在歷史管理，而不是模型選擇。
